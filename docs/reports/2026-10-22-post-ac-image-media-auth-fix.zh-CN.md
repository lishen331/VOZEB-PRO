## 2. 关键根因：ModelBay 图片媒体代理 403

### 2.1 证据

生产中 `gpt-image-2.5-sunburst` 经 ModelBay 路由到上游模型 `gpt-image-2-image-to-image`。5 条真实任务在 A/C 部署后的生产环境失败，任务 ID：

- `3281dccb-6054-49ea-b959-1f47d3eb497c`
- `ff5d4d4f-fae9-4a16-ba8e-664f56397a6f`
- `d70f11c9-7df8-4165-8d01-8d7bb720fee8`
- `d4289417-63ef-4e78-bb12-29d0623d1611`
- `1a763ebf-71b2-4344-b049-17ee85f9903d`

脱敏链路证据在本机私有 Run 目录：`image-to-image-failures-sanitized.jsonl`、`image2i2-diagnostic-host-only.jsonl`。证据链为：上游 `api.modelbay.io` 的创建/轮询响应均正常返回 HTTP 200 JSON，任务已拿到上游结果；随后平台通过本机 `/api/ai/system/<channel>/_media` 读取结果，服务端返回 HTTP 403 JSON、0 bytes，终态 `media_http_error`。失败点在平台自有的签名媒体授权校验，不是浏览器图片渲染，也不是已有证据可支持的 ModelBay 生图请求拒绝。

数据库只读记录进一步证明配置身份不一致：任务 `config.logicalModel` 为 `gpt-image-2.5-sunburst`，而 `config.model`/`routeLogicalModel` 为实际路由上游名 `gpt-image-2-image-to-image`；失败记录的同一上游渠道为 ModelBay。无凭据/签名 URL 被复制到仓库。

### 2.2 根因

图片结果服务签名令牌时调用 `generationModelId(task.config)`，其语义是“逻辑模型优先”；而媒体代理授权端对照持久化任务配置中的 `config.model`（真实上游模型）校验。经备用路由/逻辑名与上游名不一致时，服务端签名声明和授权端期望值不同，合法的结果媒体请求被平台自身拒绝 403。

### 2.3 修复

`image-task-result-service.ts` 生成媒体代理签名时改用 `task.config.model`，让签名绑定实际调用的上游模型，与媒体授权服务的任务校验契约一致。只影响生成结果媒体读取，不改变路由选择、扣费模型、用户权限或任何普通媒体链路。

新增 `image-task-result-media-auth.test.ts`，构造“逻辑模型 `gpt-image-2.5-sunburst`、上游模型 `gpt-image-2-image-to-image`”场景。

- RED：旧代码回归测试失败，实际签名参数被证实为逻辑模型 `gpt-image-2.5-sunburst`，预期上游模型。
- GREEN：修复后定向测试通过。
