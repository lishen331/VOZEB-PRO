# 绑定验证需求复盘与方案建议

- 日期：2026-10-06
- 对照文档：`docs/development/binding-verification-staging-root-cause-2026-10-06.zh-CN.md`（以下简称"原文档"）
- 性质：需求理解和方向建议，不是实施细节。标注"待确认"的条目需要负责人拍板后再开发。

## 1. 我理解的真实需求

管理员给渠道绑定好模型后，需要**一次低成本的真实生成**来回答两个问题：

1. 学生在画布里选这个模型，能不能出结果？
2. 这个绑定具体支持哪些能力（文生视频、图生视频、多图参考、视频参考），用什么参数？

验证是为"可用性"服务的工具，不是合规审计。它必须满足：

- 测试结果可信：通过 = 画布真能用，失败 = 真有问题，并能看出问题在哪一层。
- 不挡路：失败或未测试都不能锁住编辑、保存、启用、调并发上限。
- 省钱：发出前能看到参数和预估费用，协议明确不支持的组合在发出前就提示，不白扣费。

## 2. 原文档的偏差

| # | 原文档做法 | 问题 |
|---|---|---|
| D1 | 把问题定为"验证器误判"，修法是继续加强代理边界的报文断言（digest 写进 multipart 文件名、逐项消费证据） | 验证器本身就是这次误报的来源。越严格、越复杂，越容易出新的误报，也越难维护。用户要的是"能不能出结果"，报文是否逐字节一致是次要问题。 |
| D2 | 验证用 runner 自己构造请求，代理边界不符就返回 422 | 走的不是画布的真实生成链路。通过了也不能证明画布可用，失败也不能证明不可用。两头都不可信。 |
| D3 | 修完后视频默认示例素材仍是 3 张（原文档第 117 行） | OpenAI `/videos` 协议只允许 1 张参考图，默认值和协议还是冲突，用户第一次点测试大概率仍失败。 |
| D4 | 5 秒被归一化为 8 秒，只在弹窗里加了提示 | 没回答同一问题在画布侧的影响：学生选 5 秒时，是否也被静默改成 8 秒并按 8 秒扣费？这直接影响课堂费用和体验。 |
| D5 | 验证结论绑定在配置指纹上，而指纹包含 `capabilityProfile`（含 `concurrencyLimit`） | 运营调并发上限、权重、优先级这类参数，就会让验证"失效"。10-06 渠道并发测试就是因此被 400 挡住。现在代码已改为只警告，但每调一次上限都会弹"尚无成功生成记录"，属于噪音。 |
| D6 | P1/P2（能力矩阵、参数控件、诊断回看）排在后面，没有和 10-08 课堂的优先级对齐 | 课前真正要紧的只有"验证不挡上课"，其余都可以课后再做。 |

## 3. 建议方向

### 3.1 验证走真实链路，以产物为准

- 验证任务通过 `scheduleGenerationTask → generation worker → /api/ai/system/...` 执行，和画布用的是同一条链路。可以加 `surface=binding-verification` 标记，便于区分和计费归属。
- 判定标准：拿到可下载、能打开的产物（图片可解码、视频有时长、文本非空）即为通过。
- 报文审计降级为**诊断记录**：记录"选择的参数和素材 → 适配器转换后的实际报文摘要 → 上游状态和响应摘要"。差异以黄色提示显示，**不在发送前用 422 拦截**。

### 3.2 只保留真正省钱的前置检查

发送前只拦截协议**明确声明不支持**的组合，例如 OpenAI 视频协议传了多张图，或时长不在 4/8/12 中。拦截时要给出合法选项，让用户一键改。其他情况一律发出去，由真实结果说话。

### 3.3 参数与能力来自协议声明

- 分辨率、时长、比例、参考素材数量和类型，从协议或模型能力声明里读取，默认取最便宜的合法值。不再硬编码 `480p/5s/3 张图`。
- 发生归一化（5→8 秒）时，在确认页明确显示"实际将按 8 秒提交，费用按 8 秒计"。
- 能力矩阵按项展示：已验证 / 未验证 / 协议不支持。"视频参考"只有真实提交过参考视频并成功才算已验证。

### 3.4 指纹只覆盖"影响能否生成"的字段

指纹保留：`baseUrl`、`apiFormat`、凭据摘要、`upstreamModel`、协议和请求模板（advanced config 中影响报文的部分）。

指纹排除：`concurrencyLimit`、权重、优先级、启用状态等运营参数。调这些参数不应让验证失效，也不应弹警告。

### 3.5 画布侧同步检查（D4）

确认画布视频生成在 OpenAI 协议下的时长处理，以及计费按哪个时长算。如果存在静默归一化，画布的选项要按协议能力展示，或在提交时提示。

## 4. 优先级建议（对齐 10-08 课堂）

| 时间 | 事项 |
|---|---|
| 课前（10-07 前） | ① 确认 staging/生产镜像里验证是"仅警告"，不阻断启用和调并发上限。② 把 `concurrencyLimit` 等运营参数移出指纹（改动小，压测要频繁调上限，必须先做）。③ 默认视频素材按协议上限取值。其余一律冻结。 |
| 课后 | 3.1 改走真实链路；3.2 精简前置检查；3.3 能力矩阵和参数控件；诊断回看。 |

## 5. 待负责人确认

1. 验证的定位是否认同"可用性工具，以产物为准"，而不是"报文严格一致"？如果确实要保留严格报文审计（例如防渠道商偷换模型），需要说明具体场景，再决定哪些字段要强校验。
2. 验证产生的费用记在哪：管理员账户、系统账户，还是不计费？
3. 画布里 5→8 秒的归一化，是否允许？是否要在画布侧提示？
4. 课前是否同意只做第 4 节"课前"那三项，其余冻结到课后？
