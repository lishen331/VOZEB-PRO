## 3. 根因（代码层）

### 根因 A：参考素材在多媒体格式转换后被验证器漏认

- `/api/ai/system/[channelId]/[...path]` 在发起上游请求前调用 `assertBindingVerificationSubmission`；校验失败直接返回 422。
- `video-task-openai.ts` 把图片 URL 下载为图片文件，写入 multipart 字段 `input_reference`。上游实际请求体不再包含原始图片 URL。
- `binding-verification-authority.ts` 虽然统计 multipart 图片文件和二进制 digest，但只对没有 `run.input` 的旧式 fixture 流程使用 `imageFiles` 兜底；有 `run.input` 时会把计数覆盖成“匹配 URL/URL 映射/已登记 referenceEvidence 的条数”。
- 视频输入路径没有像图像输入路径一样，提前记录“每个输入素材的内容 digest”，因此合法 multipart 文件无法与用户选择的参考素材建立一一对应关系，误报缺素材。

修复原则：校验“选中的每个素材的身份”是否在最终 wire payload 中逐个出现；不能把文件总数当成素材身份，也不能只按 URL 判断。对 multipart 应在转换前/后记录安全的 SHA-256 映射，并在代理边界核对字段、数量、类型和 digest。只保存脱敏结构与摘要，不保存 API Key、Authorization 或媒体原始内容。

### 根因 B：固定的 5 秒与 OpenAI 视频适配器互斥

- 绑定验证 runner 固定发 `videoSeconds: 5`，并强制分辨率 `480p`。
- `video-task-openai.ts` 注释明确该协议接受 `4 / 8 / 12` 秒；`normalizeOpenAiVideoSeconds(5)` 会把 5 秒变成 8 秒。
- 验证代理随后要求上游 wire payload 的时长**必须精确为 5 秒**，所以对这类适配器而言验证必然失败。这是平台对适配器做过规格变换后仍用原始规格断言导致的自相矛盾，不是模型生成失败。
- 前端目前只显示 `480P` 标签，没有可配置的分辨率/时长控件；用户无法选择模型真正支持的测试规格。

修复原则：在协议能力层先解析该绑定可原样使用的分辨率、时长、比例与参考素材规则；由用户选择或提供低成本默认值。提交后校验“实际提交的规范化参数 == 用户确认的有效参数”，不要求所有协议统一固定成 480p/5 秒，也不允许无提示地归一化或丢弃参数。若当前协议不能承载所选参数，发送前给出可理解的协议限制及可选合法值，不发起生成、不扣费。

### 根因 C：通用视频模板与协议专属参考能力不匹配

- 验证弹窗对所有 video 能力都按 3 个 fixture 计数；某些输入路径的默认素材也预置多张图片。
- OpenAI `/videos` multipart 适配器当前明确限制最多 1 张参考图，且只提供 `input_reference` 图片字段，不能由此推断支持视频参考。
- 因此“视频模型”这一粗能力分类不足以决定测试输入；需按协议、端点、模型能力声明与已确认参数规则生成测试计划。

修复原则：分辨并展示至少 `文生视频`、`图生视频`、`视频参考`、`多图参考` 能力。单次请求可覆盖多种能力时应优先复用同一生成来节省费用；不支持某能力时允许选择更低阶测试，而不是强塞多张素材。若要证明视频参考能力，必须真的提交参考视频，并通过线上实测/协议证据确认，不能由一张参考图测试推断。

## 4. 推荐修复设计

### A. 先分析、再生成（AI 协议助手）

1. 输入 API 文档、URL 或 API 示例后，提取能力、协议端点、模型能力、接受的参考素材类型/数量、时长/分辨率/比例约束、结果查询方法。
2. AI 推断必须区分“文档明示”“由请求/响应实测”“未验证推测”；保留分析记录，可回看、编辑，再应用到当前渠道的单个模型绑定。
3. AI 分析不能单独作为“已实际可用”的证据；真实生成成功后才记为通过。

### B. 成本可控的分层实测

1. 在真正发起任务前展示生成计划、所需素材、预估费用（若无法估算则明确显示未知）、用户确认按钮。
2. 默认选最便宜且能回答当前问题的一次测试；参数来自该绑定能力，不硬编码 `480p/5s`。
3. 先用一个组合请求覆盖最多能力（例如视频+图片+提示词，前提是协议确实允许）；失败且返回明确的本地协议限制时，不重复扣费，允许调整为低阶能力重测。
4. 视频参考是独立能力：只有包含真实参考视频的成功请求才标记已验证；没有验证的能力保持“未知”，不要误标支持或不支持。
5. 测试结果与诊断记录在弹窗内持久保留。失败、待确认只展示提示及重测选项，不锁住协议修改、素材选择、弹窗保存或模型启用。

### C. 启用策略

- 已启用的绑定不得被验证门禁意外拦截或自动关闭。
- 未成功生成实测时允许管理员启用，但明确提示“尚无成功生成记录，可能无法使用”；这是用户要求的可用性优先策略。
- 实测失败不能伪装成通过；配置修改后，旧通过记录按配置指纹失效，但历史诊断仍可查询。

## 5. 开发拆分建议

1. **P0：修正错误的本地拒绝**
   - 重构代理边界的素材证据：URL 与 multipart file 分别验证，按 sha256 与输入素材逐个匹配。
   - runner 为图片、视频统一生成 `referenceEvidence`；禁止以“文件数够了”替代引用身份匹配。
   - 在 OpenAI 适配器归一化参数之后，按协议有效参数验证实际请求，不再固定等于 5 秒。
   - 明确哪些错误发生在上游调用前，并在诊断中记录 `upstreamRequestStarted=false`、`adapter/protocol`、`submittedReferenceTypes/count`、实际参数和失败节点。

2. **P1：弹窗模型能力与参数 UI**
   - 依据分析结果展示能力矩阵；用户可选择要测的能力及素材。
   - 将分辨率、时长、比例变为协议/模型约束下的控件；选项无效时禁用提交并说明原因。
   - 允许“只测文生视频 / 图生视频 / 视频参考”等单项或成本最低的覆盖组合；绝不能静默删素材。

3. **P2：可回看诊断与启用提示**
   - 保存 AI 分析快照、请求参数、节点事件、实际返回摘要及生成产物引用。
   - 未测试也可启用，点击时警告而不阻断；失败记录不锁操作。
   - 多设备配置冲突采用显式版本/指纹检查与明确冲突提示，而不是强制用户刷新后才能继续。

## 7. 当前结论与下一步

测试环境中观察到的近期失败，至少有两类是验证器在上游请求前的本地拦截：OpenAI multipart 把 5 秒归一化成 8 秒但平台仍按 5 秒核验，以及素材转为 `input_reference` 后因没有来源身份映射而被误判缺失。这些旧失败记录仍不能作为上游不支持的证据。

**P0 后端误判修复已完成**：runner、适配器和代理边界现在共享有效时长；OpenAI multipart 文件名携带所选源图 SHA-256 标识，代理逐项消费 URL、二进制或来源标识证据，拒绝缺失/错误/复用的素材凭证；校验器可从 OpenAI `size=854x480` 识别 480p。相关回归覆盖通过。UI 已按请求模板识别 multipart 协议，展示有效 8 秒并提示 5→8 秒归一化；视频默认示例素材为 3 张，失败后协议/素材/重测控件恢复可编辑。

弹窗能力/参数 UI、验证结果可回看、脱敏诊断导出和启用提示已在本轮代码中补齐，并由本地回归覆盖。本地回归通过并不等于真实上游已实测通过：本轮未运行真实计费生成、未修改 staging/production 数据。GitHub 推送/合并与生产发布是独立的交付步骤。

- 绑定保存校验已改为**提示性策略**：启用新绑定、启用状态下执行配置变化、或创建新的启用绑定时，若当前配置没有成功生成凭证，保存不再被验证策略拒绝；API 返回 `bindingVerificationWarnings`，其中只包含模型/绑定/渠道标识、单向配置指纹和脱敏提示，不包含 Key、Authorization、提示词或媒体原文。

### 建议验收顺序

1. 在测试环境保存一个未测试的新绑定，确认 HTTP 200、配置确实保存，并检查响应中的 `bindingVerificationWarnings`；页面应显示“尚无成功生成记录，启用后可能无法使用”。
