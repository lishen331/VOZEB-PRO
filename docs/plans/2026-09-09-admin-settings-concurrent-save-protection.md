# 管理后台模型渠道并发保存保护开发方案

- 日期：2026-09-09
- 范围：管理后台「模型渠道」配置及其关联的逻辑模型、默认模型配置
- 状态：待确认，确认后开发
- 目标：解决同一管理员账号在多个浏览器、标签页或 IP 同时编辑时，旧页面保存覆盖新配置的问题

## 1. 已确认的问题

同一个管理员账号在多个页面同时打开模型渠道配置时，每个页面持有一份打开时读取的完整配置快照。

复现链路：

1. 页面 A、页面 B 同时读取配置版本 A；
2. 页面 A 删除渠道并自动保存，数据库变为版本 B；
3. 页面 B 仍持有版本 A；
4. 页面 B 点击「保存更改」；
5. 服务端把页面 B 的旧 `systemChannels`、`logicalModels`、`defaultModels` 等完整快照当作最新配置写回；
6. 页面 A 的删除和其他新配置被旧快照覆盖。

已在测试服务器真实复现：删除渠道后，旧隐私窗口保存，已删除渠道重新出现在数据库中。

## 2. 第一版解决方案

采用「服务端 revision 乐观并发校验 + 保存成功后广播刷新」的组合方案。

### 2.1 revision 乐观并发校验

为模型渠道配置维护单调递增版本号 `revision`。

配置读取时返回：

```json
{
  "settings": {},
  "revision": 42
}
```

页面保存时带上读取时的版本：

```json
{
  "revision": 42,
  "systemChannels": [],
  "logicalModels": [],
  "defaultModels": {}
}
```

服务端在同一数据库事务中：

1. 锁定配置行；
2. 读取当前 revision；
3. 比较请求 revision；
4. 一致时保存并将 revision 加一；
5. 不一致时回滚并返回 `409 Conflict`。

版本不一致时不得执行任何渠道 upsert 或删除。

### 2.2 保存成功后广播更新

保存成功后广播：

```json
{
  "type": "settings-updated",
  "revision": 43,
  "updatedAt": "2026-09-09T...Z"
}
```

广播范围：当前管理员账号对应的管理后台配置页面。由于当前系统使用同一管理员账号，第一版可以按管理后台配置更新事件广播；不得广播密钥和完整配置正文。

### 2.3 页面间刷新策略

#### 页面没有未保存修改

收到更高 revision 后自动重新获取最新配置，并更新页面状态。

#### 页面存在未保存修改

不得静默覆盖当前编辑内容，显示提示：

```text
配置已被其他页面更新
服务器已有更新，你当前还有未保存修改。

[刷新为最新配置] [保留当前编辑]
```

第一版不实现字段级自动合并。

#### 广播不可用

使用低频 revision 检查作为兜底，例如 10–15 秒检查一次版本号；只读取版本元数据，不拉取完整渠道密钥和配置正文。

### 2.4 删除渠道统一走并发保护

删除渠道虽然由前端点击删除后自动保存，但它仍然必须携带 revision，并走同一个保存事务：

```text
删除确认
→ 提交删除后的配置 + revision
→ 服务端校验 revision
→ 成功：删除/保存、revision + 1、广播
→ 失败：409，不写入任何配置
```

删除成功后，其他页面自动刷新；旧页面再次保存时必须因 revision 不一致而被拒绝。

## 3. 后端改动范围

### 3.1 数据结构

优先在现有 `vozeb_pro_app_settings` 表增加：

- `settings_revision bigint not null default 1`
- 可复用现有 `updated_at`，不新增重复时间字段

如果数据库兼容层已有版本字段，则统一复用，不重复建字段。

### 3.2 设置读取接口

调整管理后台设置 GET 接口，返回：

- 当前配置；
- `revision`；
- `updatedAt`（可选，用于调试和展示）。

不得返回 API Key 明文。

### 3.3 设置保存接口

调整 PATCH 接口：

- 要求模型渠道相关保存请求携带 `revision`；
- 缺失 revision 时返回明确错误，不允许旧客户端继续全量覆盖；
- revision 不一致返回 `409`；
- 响应包含最新 revision；
- 不泄漏密钥和完整配置差异。

### 3.4 事务与锁

保存必须在既有 PostgreSQL 事务中完成：

```text
SELECT app_settings ... FOR UPDATE
→ compare revision
→ update app settings
→ upsert submitted channels
→ delete only channels intentionally removed by this save
→ revision + 1
→ commit
```

当前 `deleteSystemModelChannelsNotIn` 的全量删除行为暂时保留在兼容保存路径，但只有 revision 校验通过后才允许执行。后续可再拆分为显式删除接口，不纳入本次第一版范围。

### 3.5 审计日志

保留现有 `admin.settings.update` 事件，并补充非敏感元数据：

```json
{
  "revisionBefore": 42,
  "revisionAfter": 43,
  "fields": ["systemChannels", "logicalModels", "defaultModels"],
  "source": "admin-settings-page"
}
```

不得记录：

- API Key；
- Webhook Secret；
- 密钥明文；
- 完整配置正文。

## 4. 前端改动范围

### 4.1 页面状态

后台模型渠道工作区维护：

- `loadedRevision`：最近一次读取的服务端版本；
- `hasUnsavedChanges`：当前页面是否有本地编辑；
- `remoteRevision`：收到广播或兜底检查得到的远端版本。

### 4.2 保存成功

保存成功后：

1. 更新本页面配置和 `loadedRevision`；
2. 清除未保存标记；
3. 显示成功提示；
4. 广播配置已更新事件。

### 4.3 409 处理

收到 `409 Conflict` 时：

1. 不覆盖当前编辑状态；
2. 不自动重试保存；
3. 提示配置已被其他页面更新；
4. 提供「刷新为最新配置」和「保留当前编辑」；
5. 记录一次非敏感客户端诊断信息。

### 4.4 删除成功

删除操作成功后：

- 更新当前页面 revision；
- 更新当前列表；
- 通过同一广播机制通知其他页面；
- 不额外触发第二次重复保存。

## 5. 广播实现建议

按实现成本分层：

1. 同源同浏览器标签页：`BroadcastChannel`；
2. 不同浏览器或不同 IP：服务端 SSE `/api/admin/settings/events`；
3. SSE 断开或不支持：10–15 秒 revision 兜底检查。

事件只包含：

- 事件类型；
- revision；
- updatedAt。

不包含：

- 渠道 API Key；
- 完整模型配置；
- 任何敏感凭据。

## 6. 验收标准

### 并发覆盖

- 两个浏览器打开同一账号的配置页；
- A 保存后 revision 增加；
- B 不刷新直接保存；
- B 必须收到 409；
- A 的配置不能被 B 覆盖；
- 数据库不得出现 B 的旧快照。

### 删除场景

- A 删除渠道并自动保存；
- B 仍显示旧渠道；
- B 点击保存；
- B 收到 409；
- 已删除渠道不能恢复。

### 自动刷新

- A 保存成功；
- B 无未保存修改时自动刷新为最新配置；
- B 有未保存修改时不被静默覆盖，并出现提示。

### 配置完整性

- 渠道名称不变；
- 渠道协议不变；
- 模型名称不变；
- 逻辑模型绑定不变；
- 默认模型不变；
- API Key 不展示、不写入日志。

### 回归测试

至少覆盖：

- GET 返回 revision；
- PATCH revision 一致成功；
- PATCH revision 不一致返回 409；
- 删除保存 revision 校验；
- 同一事务不会部分写入；
- `BroadcastChannel` 事件处理；
- SSE 事件处理；
- 未保存编辑状态不被远端刷新覆盖；
- 旧客户端缺失 revision 的明确失败行为。

## 7. 迁移与兼容

- 已有配置数据不变；
- 为现有 `app_settings` 初始化 `revision = 1`；
- 不自动重命名渠道；
- 不自动恢复或删除模型；
- 不修改 API Key；
- 发布后首次成功保存将 revision 更新为 2；
- 旧客户端保存请求缺失 revision 时拒绝，避免继续产生无版本覆盖。

## 8. 本次不做

- 不实现字段级自动合并；
- 不实现多人实时光标/编辑锁；
- 不实现复杂配置 diff 编辑器；
- 不改变模型协议业务逻辑；
- 不修改 RunningHub、昱梦、兔子 API 或其他渠道的名称和模型配置；
- 不在开发阶段直接恢复生产配置；
- 不记录 API Key 或完整配置快照到审计日志。

## 9. 开发前置条件

1. 先导出当前服务器渠道和逻辑模型只读快照；
2. 确认恢复后的正确渠道列表；
3. 在本地和隔离测试数据库完成 revision 迁移；
4. 完成并发保存回归测试；
5. 再部署到测试服务器；
6. 用两个浏览器实际复现并确认旧页面保存返回 409；
7. 最后再恢复/重新配置渠道。

## 10. 交付物

- 数据库迁移；
- 后端 revision 并发保护；
- 前端自动刷新与冲突提示；
- BroadcastChannel/SSE/兜底检查；
- 自动保存/删除统一并发校验；
- 单元测试、接口测试和浏览器回归测试；
- 配置变更审计增强；
- 测试报告和部署记录。
