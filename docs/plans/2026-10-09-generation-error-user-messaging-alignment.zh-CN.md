# 生图失败、“查不到上游 ID”根因与最终修复方案

日期：2026-10-09（北京时间）  
状态：方案已对齐，等待实施；本文件只记录方案，不代表代码已经修改或生产已经发布。  
合并自：[2026-10-08 上游 ID 丢失根因](./2026-10-08-image-upstream-id-loss-root-fix.zh-CN.md)、[提交结果未知改为退款 + 自动重试](./2026-10-08-image-unknown-submission-refund-retry.zh-CN.md)。内容冲突时以本文为准。

## 一、根因

### 1.1 结论

1. “查不到上游 ID”不是 ID 丢了，而是同步接口本来就没有 task ID。生产三个图片渠道（模汇X中漫 / easyart、兔子、ModelBay）的所有图片模型都配置为 New API 同步接口 `/images/generations`、`/images/edits`，没有一个模型声明 `queryPath`。同步接口的响应 body 就是唯一交付，这次没拿到图，之后也查不回来。
2. 真正的缺陷在平台：同步请求失败后，系统按异步任务的规则把它挂进 `needs_review` 等 ID。没有 ID 的 `needs_review` 是死状态，Worker 不再认领，用户“检查状态”返回 409，只能人工结束。今天 101 条失败里有 76 条是这样结束的，用户看到的是“人工核查后结束本次任务”。
3. “结果未知”的判定过宽。[generation-submission-error.ts](../../web/src/lib/server/generation-submission-error.ts) 只把 400/401/403/404/405/413/415/422/429 当作明确失败，451 内容安全拒绝和 502/503/504 都算“结果未知”，于是明确失败也被挂起。
4. 今天真正与上游异步能力有关的只有 ModelBay：任务制模型 `gpt-image-2-*-to-image` 只接受异步端点，生产仍走同步端点，结果是直接 400 或 600 秒超时。代码 `ac59a9f1` 已有 `modelbay-image-task` / `tuzi-image-task` 协议，但生产渠道还没切换。
5. 失败最多的是 easyart 的生成耗时贴着网关上限（见 1.2），与 task ID 无关。easyart 目前没有已验证的图片异步接口，切协议解决不了。

## 二、对“必须切换异步协议”判断的评估

截图的数据基本准确，“查不到上游 ID 还没有从生产根本解决”的结论成立。有三点需要修正：

1. 把“保存的 `upstream_task_id` 为 0 条”当作故障指标不对。同步接口本来就没有 task ID，异步链路全部上线后，easyart 的同步任务仍然是 0。验收应看“没有任务因为缺 ID 卡住或需要人工结束”，而不是“所有任务都有 task ID”。
2. “根因上必须完成异步协议切换”只适用于有异步接口的上游（ModelBay 已确认，兔子待验证）。按 1.2 的表，切异步最多解决 ModelBay 约 13 条，占今天失败的 13% 左右。失败最多的 easyart 504 / 超时（50 条）和额度不足（17 条）都不在这个范围内。
3. 截图里的链路只有成功分支，缺少失败分支，也没覆盖同步上游。完整链路应是：

```text
有异步接口：提交 → 保存 upstream_task_id → Worker 查询同一任务
            ├─ 成功：在结果 URL 有效期内转存 OSS → 保存 object key → 成功
            └─ 失败 / 查询窗口超时：退款 → 失败终态
没有异步接口：同步请求
            ├─ 完整收到图片 → 转存 OSS → 保存 object key → 成功
            ├─ 明确失败（4xx、451）→ 退款 → 失败终态
            └─ 结果不可追回（5xx、超时、响应中断）→ 退款 → 自动重试 1 次 → 仍失败则失败终态
```

两条链路都不允许进入“无 ID 的 needs_review”。上游没有异步接口时的完整处理见第九节。

## 四、总体原则

用户前端只看到简短、可执行的提示，不展示平台内部状态、供应商协议、任务 ID、存储系统或诊断细节。

后台生成运维、任务详情、生成日志和诊断事件继续保留真实错误，方便定位、对账、退款和重试。

不要为了让提示“看起来有原因”而编造具体原因。无法确定真实原因时，统一使用“网络异常，请点击重试”。

## 五、用户前端只保留三类提示

| 识别出的后端情况 | 用户前端提示 |
|---|---|
| 网络失败、超时、响应中断、未知异常、参数无法确认、参考图问题、输入内容问题、平台解析失败、OSS 保存失败、上游结果无法追回 | **网络异常，请点击重试。** |
| 当前模型协议不匹配、模型暂时不可用、模型没有开通、异步模型误走同步接口 | **当前模型暂时不可用，请切换模型后重试。** |
| 上游明确返回内容安全拒绝 | **内容未通过安全审核，请修改描述或更换参考图后重试。** |

以下内部信息不得直接展示给普通用户：

- `needs_review`
- `submission_outcome_unknown`
- “上游提交结果不确定”
- “人工核查后结束”
- “已退款”
- `ECONNRESET`、`RequestTimeout`、堆栈溢出
- `response_format`、`/image/submit`、`/v1/images/generations` 等协议细节
- 上游名称、request ID、task ID、OSS、Bucket、签名 URL

用户点击重试时，沿用失败任务已有的重试身份和重试规则，不能因为文案统一就重复创建不受控制的新任务。

## 六、后台必须保留真实问题

后台任务详情和诊断记录至少保留：

- 原始错误文本和安全处理后的展示文本；
- 统一错误类别；
- 渠道 ID、模型 ID、上游 request ID 和上游 task ID；
- 上游 HTTP 状态、响应是否完整、已读取字节数；
- 解析、图片规范化、OSS 上传和媒体登记各阶段状态；
- 积分扣费、退款和供应商账单对账状态；
- 是否允许重试以及重试次数。

后台示例：

```text
ModelBay: model gpt-image-2-text-to-image is only available on asynchronous task endpoints
```

前端只显示：

```text
当前模型暂时不可用，请切换模型后重试。
```

后台示例：

```text
外部存储上传失败：ECONNRESET
```

前端只显示：

```text
网络异常，请点击重试。
```

## 七、`needs_review` 的处理

用户不再看到“待确认”或“人工核查”。后端判断一个任务该不该挂起，不看“有没有拿到 ID”，看“之后还有没有办法查回结果”。

### 7.1 可继续查询的异步任务

真正保存了上游 task ID、查询路径和渠道协议的任务，Worker 继续查询原任务。前端显示“生成中”，直到成功或确定失败。

没有 task ID、但渠道声明了 `requestIdQueryPath` 且本次已存下 request ID 的任务，同样算可追回。目前生产三个渠道都没有声明。

### 7.2 不可追回的任务

没有上游 task ID、没有有效查询路径，或已经确认无法继续查询的任务，进入失败终态，不再写 `needs_review`。代码中有三处在没有 ID 时写 `needs_review`，都要改为分流：

- [image-task-runtime.ts](../../web/src/lib/server/image-task-runtime.ts) 提交异常的 best-effort 写入
- [generation-task-recovery-service.ts](../../web/src/lib/server/generation-task-recovery-service.ts) Worker 发现任务停在 `submitting` 且没有 ID
- [generation-task-recovery-service.ts](../../web/src/lib/server/generation-task-recovery-service.ts) 提交抛异常且没有 ID

```text
没有上游 task ID
  ├─ 可追回（7.1）→ 保持 needs_review，按 request ID 查询
  └─ 不可追回
       ├─ 明确失败（4xx、451）→ 退款 + 失败终态，不重试
       └─ 结果未知（5xx、超时、响应中断）
            ├─ attemptNo < 2 → 退款，回到 created，Worker 换渠道重新提交
            └─ 已重试过 → 退款 + 失败终态
```

重试复用现有“上游明确失败自动重试 1 次”的机制，退款、换渠道、清上游身份都是既有逻辑。实现草稿在 `git stash@{0}`（image-unknown-submission-refund-retry），需要补上“可追回”分支后再应用。

用户积分这一侧，系统代理在上游非 2xx、网络异常、请求中止时已经立即退款，挂起并没有保护用户。重试的代价是平台可能被中转多扣一次（上游已生成但平台没收到），每个任务最多一次。

不可追回的任务前端显示：

```text
网络异常，请点击重试。
```

后台保留真实提交结果、request ID、响应事件和账务状态。

### 7.3 异步查询超时与存量

异步任务达到查询窗口后进入失败处理。前端仍使用“网络异常，请点击重试”，后台显示实际查询超时和最后一次上游状态。

数据库内部是否继续保留 `needs_review` 作为历史兼容状态，需要实施时单独处理；该状态不得再作为用户可见状态，也不能让不可追回任务长期停留。

存量无 ID 的图片 `needs_review` 用一次性脚本处理：条件为 `task_type = 'image' AND execution_phase = 'needs_review' AND upstream_task_id IS NULL`，且不满足 7.1 的可追回条件，调用既有失败路径退款并结束。退款带幂等键，已退过的不会重复退。先 dry-run 输出清单，正式执行前单独确认。

## 八、ModelBay 异步协议

ModelBay 的任务制图片模型不能继续调用同步图片端点。已确认的协议方向是：

```text
POST /image/submit
GET  /image/fetch/{task_id}
```

提交成功后保存 `data.task_id`，之后只查询同一个任务。成功读取 `data.result_urls[]`，服务端及时下载并转存 OSS；失败读取 `data.fail_reason`。

用户不看到供应商协议错误。后台保留真实错误，例如：

```text
model ... is only available on asynchronous task endpoints
Unknown parameter: response_format
```

以上错误归类为“当前模型暂时不可用”，前端显示：

```text
当前模型暂时不可用，请切换模型后重试。
```

切换前必须在测试渠道验证模型 ID、创建字段、查询字段、运行中状态、失败状态、结果 URL、参考图、计费和退款契约。

## 九、上游没有异步接口时的处理

不是所有上游都支持“提交任务 → 返回 task ID → 查询结果”。如果上游只有同步图片接口，平台不能猜测查询路径，也不能把平台内部的 Worker 任务伪装成上游异步任务。

同步接口的真实语义是：**一次 HTTP 请求完成，响应 body 就是唯一交付结果。** 请求结束前，平台必须继续持有上游连接；平台把这次请求放进 Worker，并不会释放上游连接，也不能降低上游等待时间。

### 9.1 同步接口仍要接入时

只能采用受控的同步方案：

1. 在平台入口和渠道/模型层设置并发准入与排队，先限制同时发往同一同步模型的请求数，再创建上游 HTTP 请求。限制值必须来自供应商约束、机器容量测试或管理员配置，不凭空写固定重试次数。
2. 代理层避免重复保留多份大 body；同步 `b64_json` 要控制响应读取、解析和图片处理的内存峰值。只提高 Node heap 不是根治，必须同时控制并发和数据复制。
3. 如果供应商公开支持同步返回稳定图片 URL，优先配置 `imageResponseFormat=url`。这可以减少大 base64 响应，但仍然是同步等待；收到 URL 后还要在有效期内转存 OSS。
4. 如果同步接口在高峰期无法满足成功率和时限，暂停该模型的课堂入口，或把逻辑模型切换到已经验证的异步渠道。不能让大量请求同时打满同步连接后再用“网络异常”掩盖容量问题。

### 9.2 同步接口失败时

- 没有完整响应、没有上游 task ID 的同步失败，不能自动轮询原任务，也不能凭 request ID 猜一个查询接口。
- 已完整收到图片但 OSS 保存失败，应优先保留可恢复的结果字节/临时对象并重新执行保存；不能让用户重新生成来替代保存恢复，否则可能重复扣费。
- 请求在上游可能已生成但平台没有拿到完整结果时（504、超时、响应中断），按 7.2 退款并自动重试 1 次。2026-10-08 方案中需求方已接受由平台承担可能的第二次上游费用；重试必须使用新的尝试身份和幂等账务记录。若此决定有变化，在此处更新。
- 明确失败（4xx、451、额度不足）不重试，同样的请求再发一次结果不会变。
- 无法追回的同步任务最终进入失败终态，用户只看到统一失败文案，后台保留真实响应阶段、request ID、扣费和退款状态。

### 9.3 有异步能力但平台尚未配置

如果供应商文档明确提供异步端点，而生产绑定仍走同步端点，应视为协议配置错误：

- ModelBay 任务制图片使用 `/image/submit` 和 `/image/fetch/{task_id}`；
- 兔子 `gpt-image-2.5-sunburst` 的 `/v1/videos` 异步图片入口仍需先验证真实请求体、查询返回和结果字段；
- 模汇当前没有已验证的图片异步契约，继续按同步接口处理或暂停高峰入口。

未验证的异步接口不能上线，不能按接口名称推断 task ID、查询路径或结果字段。

代码 `ac59a9f1` 已实现 `modelbay-image-task` 和 `tuzi-image-task` 两个协议，但生产渠道的图片模型配置仍是 `newapi` 同步端点。ModelBay 切换只需在测试渠道验证后修改渠道配置；兔子需要先用真实接口确认字段。

### 9.4 各上游的处理

| 上游 | 异步接口 | 今天的主要失败 | 处理 |
| --- | --- | --- | --- |
| ModelBay | 有，已确认 | 异步模型走同步端点 400；200 后响应体卡到 600 秒 | 切到 `modelbay-image-task`，任务制模型不再走同步 |
| 兔子 | 有，待验证 | 451 内容拒绝；503 anti-bot | 451 改明确失败；异步接口验证后再切；anti-bot 联系中转 |
| 模汇X中漫（easyart） | 没有已验证的 | 504 网关超时 37 条、600 秒无响应 13 条、额度不足 17 条 | 见下 |

easyart 没有异步接口，平台侧能做的是让同步失败快速、干净地结束，并减少超时：

1. 同步失败不进 `needs_review`，按 7.2 退款、重试 1 次、失败终态。这一条把“人工结束”变成用户可见的“网络异常，请点击重试”，等待时间从最长 600 秒加人工处理，缩短为一次请求的实际耗时。
2. 超时对齐网关：easyart 网关大约在 300 秒后返回 504，本地 600 秒超时之后的等待没有意义。本地超时可以按渠道配置，easyart 建议设为略高于网关上限，避免用户多等 5 分钟。具体值以测试数据为准。
3. 配置 `imageResponseFormat=url`（代码 `b00fbad7` 已支持），前提是 easyart 确认同步接口支持返回 URL。这能减小响应体和内存峰值，但不缩短生成时间，也不能消除 504。
4. 并发准入（9.1、十）：easyart 成功任务中位耗时 269 秒，课堂高峰同时发出大量请求时，排在后面的请求更容易超过网关上限。限制同时在途请求数，让多出的请求在平台侧排队，比全部压到中转再一起超时更可控。
5. 额度不足（`token quota is not enough`）是平台在中转的余额问题，与用户无关。需要余额监控和告警，在课堂前充值；任务侧按明确失败处理，前端显示“当前模型暂时不可用，请切换模型后重试”。
6. 联系 easyart：确认能否延长网关超时，或提供带 task ID 的异步图片接口。拿到真实接口文档并在测试渠道验证后，才能按 9.3 切换。
7. 如果以上措施后高峰成功率仍不达标，把课堂默认图片模型切到已验证的异步渠道，easyart 作为候选渠道。

这几项都解决不了“同步请求失败后结果丢失”本身，同步接口的结构决定了这一点。目标是：失败快速结束、用户积分正确退回、自动重试一次、后台有完整记录，并通过并发控制和超时对齐把失败率降下来。

## 十、容量故障与用户提示

评审中确认的生产 OOM 证据属于 P0 稳定性问题：生产 App 使用 `NODE_OPTIONS=--max-old-space-size=1024`，今天 08:26 和 08:43 有两次 Node `SIGABRT` core dump，时间与两轮高并发同步大响应批次吻合。OOM 解释了部分任务在上游已经返回后丢失，但不能解释今天全部失败；协议错误、额度不足、内容拒绝和人工结束要分别记录。

P0 应按以下顺序处理：

1. 同步图片入口增加按渠道/模型的并发准入，防止 176 个大 body 同时进入一个 1GB heap 的 Node 进程；
2. 减少代理、解析、base64、图片规范化和 OSS 上传之间的重复内存复制；
3. 对 OSS 上传增加独立并发控制和可恢复保存；
4. 根据容器 cgroup 上限和容量测试决定是否提高 heap，不能只提高 heap 后继续无限接收同步请求；
5. 增加进程重启后的孤儿任务快速收敛，避免等待完整 600 秒才显示失败；
6. 异步协议和用户文案在稳定性修复之后灰度启用。

用户前端不展示 OOM、排队、OSS 或供应商错误。容量过载、网络异常、未知失败统一使用“网络异常，请点击重试”；明确模型不可用或协议未配置使用“当前模型暂时不可用，请切换模型后重试”。后台必须保留 OOM、批次大小、并发数、上游响应阶段和进程重启时间。

## 十一、内容安全和素材错误

### 11.1 内容安全拒绝

上游明确返回 HTTP 451 或明确内容策略拒绝时，任务进入确定失败，按幂等规则处理退款和日志，不自动重试。需要把 451 加入 [generation-submission-error.ts](../../web/src/lib/server/generation-submission-error.ts) 的明确失败名单，今天兔子的 7 条 451 都因为不在名单里被挂进 `needs_review`、最后人工结束。前端统一显示：

```text
内容未通过安全审核，请修改描述或更换参考图后重试。
```

不得展示供应商原文、HTTP 状态、request ID 或内部审核字段。

### 11.2 参考图和输入内容问题

不再向用户显示“请补充参考图”或供应商返回的长提示。无法确认用户是否真的缺少素材时，统一显示：

```text
网络异常，请点击重试。
```

平台在提交前能够明确判断请求不完整的场景，仍应在对应输入控件附近阻止提交；已经进入生成任务后的异常统一按上表处理，不把内部校验文案暴露到结果卡片。

## 十二、实施验收

实施后需要验证：

1. ModelBay 任务使用真实异步创建和查询，生产请求不再向任务制模型发送同步 `response_format`；
2. 兔子异步协议只有在真实接口字段验证后启用；
3. 不可追回任务进入失败，不再对用户显示 `needs_review`；没有 task ID 的图片任务不再写入 `needs_review`，课堂批量中 `manually_failed` 为 0；
4. 同步接口的 504、超时、响应中断：退款并自动重试 1 次，仍失败则失败终态；451 和其他明确失败不重试；
5. “查不到上游 ID”的验收指标是“没有任务因缺 ID 卡住或需要人工结束”，不是 `upstream_task_id` 覆盖率。异步渠道的任务应 100% 带 task ID，同步渠道（easyart）的任务为 0 属正常；
6. 中转额度不足能在课堂前告警；
7. 网络、OSS、未知错误全部映射为“网络异常，请点击重试”；
8. 模型协议错误统一映射为“当前模型暂时不可用，请切换模型后重试”；
9. 内容安全拒绝统一映射为安全审核提示；
10. 后台仍能看到完整真实错误、request ID、阶段事件和账务状态；
11. 成功、失败和重试不会重复扣费或重复创建上游任务；
12. 图片、Canvas、统一 Agent、视频和工作台的错误映射保持一致；
13. 通过本地协议 fixture、相关 Vitest、类型检查和测试环境真实小样本后，再讨论生产发布。

本结论不授权直接修改生产或发布代码。实施前仍需先形成代码改动清单、测试计划和回滚方式。
