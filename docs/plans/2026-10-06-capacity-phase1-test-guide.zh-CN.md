## 2. 步骤 1：压缩

**为什么单独测**：压缩与拆接口正交。实施文档建议先只上这一步、单独复测一次，因为 437KB 的 JSON 全是重复键名，单独压缩就可能消掉大部分读体超时。若你们已经合在一起测，这一条就作为子项记录。

### 2.1 `[curl]` 看是否真的压缩了

```bash
curl -s -H "Accept-Encoding: br, gzip" -D - -o /dev/null \
  https://<站点>/api/auth/session
```

**期望**：响应头出现 `Content-Encoding: br` 或 `gzip`。

**关键检查（容易漏）**：确认压缩发生在**响应体读取之前的链路**上。如果压缩只在内网段生效、公网段仍传原始体，**收益为零**。所以务必从**公网侧**测，不要只在服务器本机 curl。

### 2.2 `[curl]` 对比压缩前后体积

```bash
# 压缩
curl -s -H "Accept-Encoding: gzip" -o /dev/null -w "gzip: %{size_download} bytes\n" https://<站点>/api/auth/session
# 不压缩
curl -s -H "Accept-Encoding: identity" -o /dev/null -w "raw:  %{size_download} bytes\n" https://<站点>/api/auth/session
```

**期望**：两者比值明显（重复键名的 JSON 通常 8:1 以上）。

> **验收门槛**：`/api/auth/session` 实际传输体积相比 437KB **显著下降**。这一步**不要求**响应体结构有任何变化。

### 3.2 `[curl]` catalog 接口需要登录

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://<站点>/api/model-catalog
```

**期望**：`401`（未带 cookie 时）。

**为什么这条重要**：步骤 3 把未登录分支的重配置摘掉了，如果这个新 URL 不鉴权，匿名请求换个地址照样能拉走完整 `logicalModels` / `systemChannels`，等于白做。这是实施时对设计文档的有意补充。

### 3.3 `[curl]` catalog 第二次请求必须命中 304

```bash
# 先拿 ETag
ETAG=$(curl -s -D - -o /dev/null https://<站点>/api/model-catalog \
  -H "Cookie: <你的登录cookie>" | grep -i '^etag:' | sed 's/^[Ee][Tt][Aa][Gg]: *//' | tr -d '\r')
echo "ETag = $ETAG"

# 带 if-none-match 再请求
curl -s -o /dev/null -w "%{http_code}\n" https://<站点>/api/model-catalog \
  -H "Cookie: <你的登录cookie>" -H "If-None-Match: $ETAG"
```

**期望**：第二次返回 `304`。

### 3.4 `[页面]` 登录后功能没有坏

拆分接口后，模型目录改由前端并行取第二个请求再浅合并。**这是最容易出问题的地方**：

1. 登录，打开**生成页**
2. 确认**模型下拉列表有内容**（不是空的）
3. 确认**积分/费用显示正常**
4. 确认**侧栏菜单项完整**、没有闪烁
5. 确认**落地路由正确**（不会跳错页）

> `site` 与 `featureModules` 刻意留在身份侧，就是为了避免侧栏闪烁和落地跳转抖动。若出现闪烁，说明这个边界被打错了。

### 3.5 `[页面]` 登出换账号后目录不串号

1. 用**账号 A** 登录，进生成页，记下模型列表
2. **登出**
3. 用**账号 B** 登录，进生成页
4. 核对模型列表

**期望**：目录与账号 B 相符，**不是账号 A 的副本**。

> 这一条测的是缓存隔离。若串号，说明共享缓存的前提被破坏。

### 3.6 `[页面]` 管理员改配置后的生效时延（**要报实测秒数**）

**不要只写结论，要给数字。**

1. 管理员后台改一个模型配置（例如改某个模型的积分倍率）
2. 用普通账号刷新页面，**每秒或每几秒看一次**
3. 记录从「后台保存」到「普通账号看到新值」的**实际时长**

**理论值**：最长约 **330 秒**（`max-age=30` 新鲜期 + `stale-while-revalidate=300` 叠加），**不是 30 秒**。

> **不接受用 `max-age` 单独换算**，必须实测。若你们对外承诺过"30 秒内全量生效"，那个承诺是错的，要更正。
> 想更快生效应下调 `stale-while-revalidate` 或加显式失效，而不是只调 `max-age`。

### 3.7 `[curl]` 不变量守卫：catalog 与身份无关

用**不同套餐、不同角色、有/无学校上下文**的三个账号分别请求 catalog，比对响应体：

```bash
curl -s https://<站点>/api/model-catalog -H "Cookie: <账号A cookie>" | sha256sum
curl -s https://<站点>/api/model-catalog -H "Cookie: <账号B cookie>" | tr -d '\r' | sha256sum
```

**期望**：三个哈希**完全一致**。

> 这是共享缓存的前提。当前代码确实与账号无关，但 `EntitlementPlan.features` 是潜在入口 —— 将来若有人用套餐 feature 控制模型可见性，缓存会**静默串号**。仓库里已有一条常驻测试挡住这个，这里再从线上确认一次。

## 5. 步骤 4 + 6：D6（提交幂等与对账）

### 5.1 为什么验收要分层

**不能无条件要求"上游 ID 非空率 100%"。** 连接在拿到任何上游响应前就中止时，平台根本不可能持有供应商 ID。请按四层分别记：

- [ ] **第 1 层**：本地关联 ID 与提交前持久化的幂等键 **100% 完整**（完全可控，硬性要求）
- [ ] **第 2 层**：上游确实返回过的请求 ID / 任务 ID **全部及时落库，无丢弃**
- [ ] **第 3 层**：上游未返回任何 ID 的用例，明确记为「提交结果未知」，**无编造 ID、无自动重复生成**
- [ ] **第 4 层**：按请求 ID 查询与幂等重试，**仅在已验证支持的渠道启用**，未验证渠道保持关闭

### 5.2 `[DB]` 第 1、2 层：落库完整性

压测跑完后，查这几项：

```sql
-- 不能有僵尸：停在 submitting 的记录
SELECT count(*) FROM generation_tasks WHERE execution_phase = 'submitting';

-- 待对账任务：应有 reviewReason，且不编造上游 ID
SELECT id, type, execution_phase, upstream_task_id, upstream_request_id, last_upstream_status
FROM generation_tasks
WHERE execution_phase = 'needs_review'
ORDER BY updated_at DESC
LIMIT 50;
```

**期望**：
- `submitting` 僵尸记录 **0 条**
- `needs_review` 的记录里，`upstream_request_id` 与 `upstream_task_id` **至少有一个非空**（有就填，没有就留空，**不允许编造**）

**第 2 层的实测方法**：从上游侧（或中转日志）拿到「确实返回过请求 ID」的清单，与库里 `upstream_request_id` 比对，**不应有遗漏**。

> 这是本次步骤 6 的核心修复点。改动前，正常成功路径拿到 task ID 后会把响应头里的请求 ID **直接丢弃**，只有"连 task ID 都没有"的兜底分支才读它。现在所有图片协议路径都统一捕获。

### 5.3 `[页面]` 第 3 层：不确定提交不编造、不自动重生成

制造一个「提交结果未知」的场景（例如在上游响应前断开，或用恰好触发超时的渠道）：

1. 触发一个必然超时/中断的图片生成
2. 到管理端看该任务

**期望**：
- 相位记为 `needs_review`（不是永久停在 `submitting`）
- `reviewReason` 写明「提交结果未知」
- **没有**被自动重新生成
- **没有**被退款（上游可能已接单计费，退款会造成错账）

### 5.4 `[页面]` 同一 `clientRequestId` 重复提交只产生一条任务

用同一个 `clientRequestId` 连点两次提交（或重放请求）：

**期望**：只产生**一条**任务、只计费**一次**。

### 5.5 `[页面]` upsert 后 `upstream_request_id` 不被冲掉

任务提交成功、进入轮询、最终完成 —— 全程查 `upstream_request_id` 应保持不丢。

> 这一条对应实施文档步骤 4 里标记的**易漏点**：`preserveTaskExecution` 的保留列表若漏了这个列，upsert 会把它冲掉。

### 5.6 `[页面]` 步骤 6 新能力：按请求 ID 追回

**先说明现状**：`requestIdQueryPath` 是**渠道级开关，默认关闭**。没有任何渠道声明它，所以**线上目前不会触发这条路径，恢复接口行为与改动前完全一致**。这符合实施文档「只有实际支持按请求 ID 查询、且已人工验证过的渠道才启用」的要求。

因此有两种测法：

**测法一（验证开关关闭时行为不变 —— 现在就能测）**

1. 找一个「提交结果未知、没有上游任务 ID」的图片任务
2. 点「检查状态」

**期望**：仍返回 409、提示"原任务没有保存上游任务 ID，无法安全追回结果"。**与改动前一致。**

**测法二（验证新能力 —— 需先在后台配一个渠道）**

1. 在管理后台给一个**测试渠道**配置 `requestIdQueryPath`，值形如 `/requests/{{requestId}}`（占位符 `{{requestId}}`）
2. 找一个 `upstream_task_id` 为空、但 `upstream_request_id` 有值的任务
3. 点「检查状态」

**期望**：
- 平台按请求 ID 向上游查一次
- **查到** → 回填 `upstream_task_id`（`last_upstream_status` 记为 `recovered_by_request_id`），然后走既有轮询把结果取回
- **查不到** → 仍返回 409，**不伪造成功**

> **重要**：只对**实际支持该查询、且你已人工验证过**的渠道开启。未验证的渠道不要开 —— 错误配置会让恢复逻辑向上游发无效请求。

### 5.7 幂等键的现状（**不需要测发不发**）

`Idempotency-Key` + `X-Client-Request-Id` **早就在发**，不是本次新增。键的形态是 `image-task:{taskId}:attempt:{attemptNo}`，**同一 attempt 重试键不变**。文本链路同理。

若要观察，服务端日志里只应出现**幂等键本身**，**不应出现整组请求头**（中转 api_key 在同一组头里，打印整组等于泄漏密钥）。

## 6. 文本/音频/视频三条链路的现状（**本次未做**）
