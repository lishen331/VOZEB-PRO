# VOZEB PRO 开发地图与更新流程设计

## 背景

当前代码已作为独立 Git 根历史维护在私人仓库 `tjfeng741963/blue-oem` 的 `main` 分支，本地和远程服务器均运行 `vozeb-pro:local` 镜像。后续二次开发需要一套稳定的导航资料，帮助开发者从页面、API、服务、数据表和部署环境之间快速定位，同时避免把所有细节塞进一张难以维护的总图。

代码盘点基线显示 `web/src/app/api/` 当前包含 172 个 `route.ts`。主要接口域包括后台管理、公开接口、认证、短剧、计费、Agent、作品、创作运行时、画布、媒体和生成任务。

## 目标

交付三份相互引用但职责独立的中文文档：

1. 根目录 `VOZEB-PRO-开发地图.md`：面向日常二次开发的主入口。
2. 根目录 `VOZEB-PRO-接口索引.md`：面向接口定位和影响范围检查的全量附录。
3. 根目录 `VOZEB-PRO-更新部署流程.md`：面向本地、GitHub 和远程 Docker 的操作手册。

文档必须直接来自当前代码和实际部署，不复制原项目宣传内容，不包含 `.env`、安装令牌、管理员密码、数据库密码、SSH 私钥或对象存储密钥。

## 非目标

- 不修改业务逻辑、API 行为、数据库结构或 Docker 配置。
- 不为每个请求体和响应体制作完整 OpenAPI Schema；索引用于导航，不替代未来的 OpenAPI 规范。
- 不重构现有 172 个 Route Handler。
- 不在文档提交后重建 Docker 镜像，因为纯文档变更不影响运行产物。
- 不记录本地或远程真实凭据。

## 文档二：接口索引

`VOZEB-PRO-接口索引.md` 以 `web/src/app/api/**/route.ts` 为唯一枚举来源。一个 Route 文件对应索引中的一行；同一路径有多个方法时在同一行列出。

### 索引字段

- 业务域。
- HTTP 方法。
- API 路径。
- 权限类型。
- Route Handler 文件。
- 主要服务或 Store。
- 数据或外部系统边界。
- 用途摘要。

权限类型统一为：

- `公开`：无需登录。
- `用户`：要求有效 Session。
- `管理员`：要求管理员身份或细分权限。
- `Worker`：要求 Worker Token。
- `维护`：要求 Maintenance Token。
- `Webhook`：由签名、Provider 配置或内部策略验证。
- `混合`：同一路径的方法或分支使用不同权限策略。

权限分类必须根据 Route Handler 和它调用的鉴权函数判断；无法静态确认的项标记为“需结合实现确认”，不能凭路径名称猜测。

### 数量一致性

生成后重新扫描 `route.ts`：

- 当前基线应为 172 个 Route 文件。
- 索引行数必须等于扫描结果。
- 若实现期间代码数量变化，以最新扫描结果为准，并在文档顶部记录生成日期和总数。

## 文档三：更新部署流程

`VOZEB-PRO-更新部署流程.md` 记录当前真实链路：

```text
本地 main -> 本地测试/构建 -> Git commit -> 私人 GitHub origin/main
-> 远程 Git 拉取 -> 更新 Docker 镜像 -> Compose 重建服务 -> 健康验证
```

### 变更分类

1. 业务代码或依赖变更：执行对应测试、类型检查和生产构建，重新生成镜像并更新远程 App/Worker。
2. Dockerfile 或 Compose 变更：额外执行 Compose 配置校验，检查持久化卷和端口差异后更新。
3. 仅 `.env` 配置变更：不提交 Git，只重建受影响容器并核验配置是否生效。
4. 仅文档变更：提交和推送 Git，远程只需 `git pull`，不重启容器。
5. 数据库结构变更：先备份，再部署兼容代码，执行迁移并检查回滚边界。

### 必须包含的操作

- 开发前同步和工作区检查。
- 本地测试矩阵和 Docker 验证。
- 提交信息与推送规则。
- 远程 `/opt/blue-oem` 更新步骤。
- `docker compose ps`、健康接口、PostgreSQL 和 Worker 日志检查。
- 更新失败时的代码回滚、镜像回滚和数据库恢复边界。
- 密钥、管理员凭据、数据库卷和媒体卷的保护规则。

命令示例不得输出或硬编码真实密钥。危险命令如 `docker compose down -v` 明确列为禁止操作。

## 信息来源与维护规则

文档引用以下代码作为事实来源：

- 页面：`web/src/app/**/page.tsx`、布局和 Provider。
- API：`web/src/app/api/**/route.ts`。
- 业务：`web/src/lib/server/` 和 `web/src/lib/auth/`。
- 数据：`web/src/lib/server/database/`、Schema 和 Repository。
- 前端状态：`web/src/stores/`、`web/src/hooks/`、`web/src/services/`。
- Worker：`web/scripts/generation-worker.mjs` 及相关策略文件。
- 部署：`Dockerfile`、`docker-compose*.yml`、`.env.example`。

文档中的文件链接使用仓库相对路径，确保 GitHub 和本地编辑器均可定位。接口新增、删除或权限变化时，应同步修改接口索引和相关业务域导航。

## 验证策略

1. 使用代码扫描重新计算页面和 Route 文件数量。
2. 从 Markdown 提取全部 Mermaid 代码块并执行语法验证。
3. 检查文档引用的仓库路径是否存在。
4. 检查接口索引每个 Route 文件恰好出现一次。
5. 扫描文档，禁止出现 `.env` 中的真实值、管理员密码、SSH 私钥内容和访问密钥。
6. 执行 `git diff --check`，确认无空白错误。
7. 提交并推送 `origin/main`。
8. 远程服务器只执行 `git pull --ff-only`，确认提交一致；不重建或重启 Docker。
