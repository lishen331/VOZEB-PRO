# RunningHub Demo 工作流闭环嫁接设计

## 1. 背景与结论

同事提供的 `过程文件/Runninghub-demo` 已经以七条真实 RunningHub 工作流完成了“配置、拉取 JSON、提交、查询、产物展示”的闭环。当前 VOZEB PRO 已有渠道、工作流、生成任务和无限练习骨架，但后台测试和学生端调用没有稳定共享同一套工作流配置与运行路径，导致后台看似可配置、前端实际无法调用的问题。

第一版以 Demo 的工作流数据模型和后台闭环为标准：把已验证的七条流程完整纳入当前平台，保留既有平台功能和数据，不在本期先做运维收敛或删除通用能力。待后台测试到无限练习前端的完整闭环稳定后，再讨论运维简化。

## 2. 目标与边界

### 2.1 本期目标

1. 从 Demo 一键初始化七条真实工作流到平台，后续允许管理员继续编辑、新建、拉取和测试工作流。
2. 以 Demo 的 `Workflow` 配置为主模型，完整保存输入字段、节点映射、输出映射、运行选项、尺寸选项、超时、备注和 RunningHub API JSON 快照。
3. 修复“拉取工作流 JSON”“读取工作流”“后台测试”“无限练习前端调用”之间的断层，使它们复用同一条服务端执行链路。
4. 保持现有无限练习首组五张大卡片的视觉、顺序、文案和布局不变。
5. 在现有单项练习下面按系统现有设计语言增加角色、场景、道具三个资产类练习入口；角色主形象和角色多视图合并为一个“角色练习”卡片。
6. 复用当前平台的鉴权、加密渠道密钥、媒体资产、任务持久化、历史恢复、失败重试和结果组件。

### 2.2 本期不做

1. 不复制 Demo 原生 HTML/CSS 页面、顶部深色流程导航或视觉 token；学生端和后台继续使用当前 Next.js、Ant Design、Tailwind 与应用主题。
2. 不删除现有 RunningHub 后台能力、旧配置或既有渠道数据。
3. 不在本期限制管理员只能使用固定七条流程；七条是已验证初始目录，管理员仍可按 Demo 型配置新增或修改工作流。
4. 不做节点图可视化编辑器、GPU 调度、本地模型中台、运行自动故障切换或复杂工作流版本管理。
5. 不让老师、学生或学校管理员看到 API Key、Workflow ID、节点 ID、完整请求体、完整上游响应或原始 Workflow JSON。

## 4. 界面与交互

### 4.1 无限练习首页

当前“单项练习”的剧本练习、分镜图练习、分镜视频练习、配音练习和音乐练习五张大卡片完全不改：顺序、尺寸、文案、图标和交互保持现状。

在其后新增“创作资产练习”分区，沿用当前应用的卡片边框、间距、字体、浅深主题、hover 和 disabled 状态。此分区包含：

1. 角色练习：同页用紧凑 `Segmented` 控件切换“主形象”和“多视图”。
2. 场景练习：调用 `scene_main_view`。
3. 道具练习：调用 `prop_main_view`。

不采用 Demo 的编号流程条。资产练习卡片的可用性由对应工作流是否启用及当前配置是否可执行决定，学生端不显示技术细节。

### 4.2 专用表单与适配规则

通用表单只用于能直接由 `inputSchema` 表达的字段。以下已由 Demo 验证的规则作为受控专用表单和服务端适配逻辑实现：

1. 角色多视图必须取得角色主形象参考图，来源可为当前/历史角色结果或本次上传；缺少时禁止提交。
2. 角色主形象、道具主视图在无参考图时采用 Demo 同款的工作流拓扑处理，不能将上游环境中的默认文件名直接提交。
3. 分镜单镜头图的场景图为必填，并提供最多三张角色/道具图槽位。
4. 配音按有效台词句子顺序映射 `s1` 至 `s10`；停顿不占用声线槽位，每句可配置对应音色和六维情绪。
5. 分镜视频根据用户显式选择的音频开关决定是否写入音频节点和是否启用音频分支。

### 4.3 后台工作流管理

后台保留当前“上游配置 / RunningHub 工作流”入口及权限模型，但编辑体验以 Demo 的工作流后台为主，避免先要求管理员理解逻辑模型、模型协议、通用请求模板和多层绑定。

管理员操作流：

```text
配置 RunningHub 地址和 API Key
  -> 查看 / 初始化工作流列表
  -> 新建或编辑 Demo 型 Workflow
  -> 从 RunningHub 拉取最新 API JSON
  -> 保存输入、节点、输出和运行配置
  -> 上传样例素材并执行真实测试
  -> 在任务记录查看 nodeInfoList、任务状态、错误和产物
  -> 启用后由无限练习使用同一配置
```

工作流列表显示：工作流编码、名称、远端 Workflow ID、能力、无限练习入口、启用状态、超时、最近测试结果与时间、配置更新时间，以及编辑、拉取、测试、启停操作。

工作流编辑器分为：

1. 基础信息：编码、名称、远端 Workflow ID、能力、无限练习用途、启用、超时、备注。
2. 输入契约：`inputSchema`，包括字段、控件、必填、默认值、范围、选项、上传策略和描述。
3. 节点与产物：`nodeMappings`、`outputMappings`。
4. 运行配置：`runtimeOptions`、`generationSizeOptions`、特殊适配器类型和版本。
5. 上游 JSON：从 RunningHub 拉取并保存 `workflowApiJson` 快照，显示快照时间、指纹和当前映射核对状态。
6. 测试运行与任务记录：按输入契约生成真实测试表单，显示提交参数摘要、最终 `nodeInfoList`、上游任务 ID、状态、错误、脱敏诊断摘要和产物预览。

现有通用 RunningHub 字段与数据保持可读、可迁移，不在本期删除。Demo 型编辑器为主路径；协议字段只作为高级兼容区，不干扰首次闭环。

## 5. 配置与持久化模型

### 5.1 Demo 型 Workflow 聚合

平台新增或扩展工作流记录，使其能与 Demo `Workflow` 一一对应：

```text
workflowCode
workflowName
runninghubWorkflowId
inputSchema
nodeMappings
outputMappings
runtimeOptions
generationSizeOptions
timeoutSeconds
enabled
workflowApiJson
remark
source / sourceVersion
workflowJsonFingerprint
adapterType / adapterVersion
lastTest*
```

`workflowCode` 是无限练习调用的稳定业务标识，不能由逻辑模型 ID、显示名称或 Workflow ID 替代。每次提交记录工作流编码、远端 Workflow ID、配置指纹和适配器版本，保证历史任务可解释当时的执行配置。

### 5.2 初始化、兼容与迁移

1. 提供管理员显式“一键初始化 Demo 七工作流”操作。按 `workflowCode` 幂等识别已有记录，显示新增、更新和跳过差异，绝不静默覆盖管理员修改。
2. 现有 `workflowConfigs`、`modelConfigs`、逻辑模型和无限练习默认模型配置不删除。迁移期由桥接层将 Demo 型记录解析为当前任务运行时需要的配置对象。
3. 新旧结构共存时只以稳定 `workflowCode` 关联，不按提示词、显示名称或 Workflow ID 模糊匹配。
4. PostgreSQL 与文件后备都提供从已有部署结构升级的幂等迁移；已有表补列先使用明确的 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，不依赖 `CREATE TABLE IF NOT EXISTS` 改结构。

## 6. 统一运行链路

### 6.1 后台测试与前端共用执行服务

```text
Workflow code + 公开业务输入 + 稳定素材资产
  -> 解析当前已启用的 Demo 型 Workflow
  -> 专用适配器校验与业务输入转换
  -> 将需要的素材上传至 RunningHub
  -> 构建最终 nodeInfoList / 受控 workflow 变体
  -> POST /task/openapi/create
  -> POST /openapi/v2/query
  -> 解析输出、媒体落盘、更新任务与练习会话
  -> 复用当前结果展示、历史恢复和失败重试
```

后台测试只额外使用管理员身份和隔离的测试任务账本；不能拥有另一套请求构造或查询解析。测试成功的含义是同一 `workflowCode` 在学生端可走到相同的适配器、提交与查询路径，而不只是证明上游接口可以连通。

### 6.2 固定的 RunningHub 协议

Demo 已验证的官方接口：

```text
POST /task/openapi/create
POST /openapi/v2/query
POST /openapi/v2/media/upload/binary
POST /api/openapi/getJsonApiFormat
```

平台服务端负责 API Key 注入、媒体上传、响应校验和错误归一化。浏览器不直接访问 RunningHub。现有自定义协议字段仅服务兼容，不得改变 Demo 七条流程的运行行为。

### 6.3 特殊适配器

工作流记录保存 `adapterType`，共享运行服务按其调用受控适配器：

| adapterType | 对应流程 | 责任 |
| --- | --- | --- |
| `character-main-view` | 角色主形象 | 可选参考图上传与无参考图拓扑处理 |
| `character-multi-view` | 角色多视图 | 主形象必填、四视图文字映射 |
| `scene-main-view` | 场景全景 | 输出预设映射 |
| `prop-main-view` | 道具主视图 | 可选参考图上传与无参考图拓扑处理 |
| `storyboard-shot` | 分镜单镜头图 | 场景图和三张角色/道具图映射 |
| `storyboard-dialogue-audio` | 台词音频 | 有效台词到 `s1`–`s10` 的音色/情绪映射 |
| `storyboard-shot-video` | 分镜视频 | 图像、尺寸、时长、音频开关及分支映射 |

适配器接收公开业务字段和资产引用，输出完整 `nodeInfoList` 或已验证的 workflow 变体。客户端不得提交任意节点 ID、字段名、JSON 片段或上游 URL。

## 7. 权限、安全与审计

1. 仅拥有当前上游配置管理权限的管理员可以初始化、编辑、拉取、测试、启用、停用或删除工作流。
2. API Key 继续仅存储在服务端渠道设置中，页面、审计日志、任务 DTO 和错误信息只显示脱敏值。
3. 拉取 JSON 保存为服务端审计快照；不向普通用户 API 返回，也不当作浏览器可编辑的执行源。
4. 测试素材和学生素材都先变为平台受控资产，再由服务端上传上游；禁止浏览器携带外部 URL 或上游密钥。
5. 测试记录保留输入摘要、配置指纹、最终节点参数、上游任务 ID、状态、失败原因和产物；原始请求/响应中的凭据必须脱敏。

## 8. 测试与验收

### 8.1 服务端

1. Demo 七条配置的导入、差异预览、幂等重复导入和管理员修改不被覆盖。
2. 读取 JSON 使用 Demo 端点和请求体，结果快照持久化并生成指纹。
3. 七个适配器逐项验证必填输入、上传媒体替换、最终 `nodeInfoList`、无参考图拓扑、音频开关和配音槽位映射。
4. 后台测试与练习提交对同一 `workflowCode` 生成同一执行配置；使用本地 RunningHub TCP fixture 验证创建、查询、成功、失败和媒体结果。
5. PostgreSQL 集成测试覆盖迁移、读写、任务上下文和非整数数值字段；共享测试库时使用 `--no-file-parallelism`。

### 8.2 浏览器

1. 现有五张单项练习大卡片的 DOM、文案、布局和交互不变。
2. 新增角色、场景、道具卡片与系统视觉一致，桌面、390px、430px、浅色/深色主题无横向溢出。
3. 角色主形象、多视图、场景、道具、分镜图、分镜视频、配音均能从表单提交到结果组件；多视图缺少角色图时必须阻止提交。
4. 管理员能初始化、编辑、拉取 JSON、上传样例、真实测试、查看任务账本、启用/停用；刷新后状态持久化。
5. 失败任务在原会话和原记录内重试，复用稳定请求身份和工作流上下文，不新建重复练习记录。

## 9. 实施阶段

1. 定义 Demo 型工作流领域模型、迁移和七条初始化数据，不改变学生页面。
2. 将当前 RunningHub 后台编辑、JSON 拉取和测试改为调用共享执行服务，先修复闭环并以 fixture 验证。
3. 扩展无限练习的模块、会话模型和前端表单，接入七条工作流；保持首组五张大卡片不变并新增资产练习分区。
4. 完成数据库、服务端、浏览器和文档质量门禁后，再根据真实使用反馈讨论第二阶段后台运维优化。

## 10. 设计自检

1. 没有复制 Demo 的视觉页面，且明确保持现有首组练习大卡片。
2. 没有删除当前后台或旧配置，并保留向后桥接与幂等迁移要求。
3. 后台测试和用户调用必须使用同一服务、同一 `workflowCode` 和同一适配器，覆盖已识别的闭环断层。
4. Demo 的七条工作流、特殊输入和拓扑规则都有明确归属，节点 JSON 不暴露给普通用户。
5. 运维简化明确延后，不阻塞当前“先跑通完整流程”的目标。
