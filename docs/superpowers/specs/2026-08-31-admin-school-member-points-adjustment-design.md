# 平台管理员学校成员积分调整设计

## 1. 背景

平台已经具备学校租户、学校成员、个人积分、学校算力池、制作小组和生成扣费能力。当前平台管理员可以在“用户运营”中修改用户永久积分，但该入口不能先按学校定位成员，也不展示成员的学校归属，容易在跨校运营时选错账号。

本功能在“学校管理”中增加平台管理员专用的学校成员查询与个人积分调整入口。平台管理员先确定学校，再搜索该校成员并增加或扣减个人永久积分。它只补充跨校运营入口，不改变个人积分、学校算力池和制作小组额度三套账的既有边界。

## 2. 目标

- 所有状态正常的全局 `admin` 都可以查看全部学校，并查询任意学校的成员。
- 平台管理员可以按公开账号 ID、用户名、姓名或邮箱搜索所选学校的成员。
- 平台管理员可以给学校成员增加或扣减个人永久积分。
- 每次调整必须填写原因，并记录操作人、学校、成员、调整数额和调整前后余额。
- 扣减不能使个人永久积分低于零，重复提交不能重复入账。
- 每日赠送积分保持只读，不受人工调整影响。
- 学校管理员、老师、学生和普通用户不能使用或调用该能力。
- PostgreSQL 与项目既有文件 Provider 保持相同业务语义。

## 3. 非目标

本功能不建设以下能力：

- 不允许学校管理员给本校成员调整个人积分。
- 不把个人积分改成学校资产，也不新增校内积分账户。
- 不直接修改学校算力池、制作小组额度或个人垫付记录。
- 不改变商单项目的生成扣费顺序。
- 不调整每日赠送积分或套餐权益。
- 不提供批量调账、Excel 导入调账或自动发放规则。
- 不允许通过绝对余额覆盖的方式绕过增加、扣减和流水记录。

## 4. 账本边界

平台继续保持以下独立余额：

| 余额 | 所有者 | 使用方式 | 本功能是否修改 |
| --- | --- | --- | --- |
| 个人永久积分 | 用户个人 | 普通生产生成；也可由本人主动转为小组个人垫付 | 是 |
| 每日赠送积分 | 用户个人 | 按现有套餐规则使用并每日结算 | 否 |
| 学校算力池 | 学校 | 由学校管理员预拨给制作小组 | 否 |
| 小组学校额度 | 制作小组 | 商单正式生成优先使用 | 否 |
| 小组个人垫付 | 成员个人、按笔记录 | 小组学校额度不足后使用 | 否 |

平台管理员增加给成员的永久积分可以直接用于没有学校商单计费上下文的图片、视频及其他生产生成。成员如果要把这笔积分用于已关联商单制作小组的 Canvas 或短剧项目，仍需本人通过既有流程主动转入该小组的个人垫付。商单生成继续优先扣小组学校额度，再扣已确认的个人垫付，不直接读取成员当前个人余额。

无限练习继续使用 `open-source-practice`，不扣个人积分或学校算力。

## 5. 角色与权限

### 5.1 平台管理员

- 使用全局管理员 Session，不创建或伪造学校成员身份。
- 任意状态正常的全局 `admin` 都可以读取全部学校的基础列表、打开成员列表并调整成员永久积分，不要求 `education.manage` 或 `billing.manage`。
- 为支持该入口，学校列表和成员只读数据对所有平台管理员开放；新建学校、编辑学校资料、调整学校算力池等既有操作继续保持原职责权限，不因本功能放宽。
- 平台管理员可以跨学校操作，但每次请求必须携带学校 ID，并由服务端验证成员确实属于该学校。

### 5.2 学校与普通用户

- `teacher + school.manage` 的学校管理员只能通过学校端查看和管理本校成员，不能看到积分调整按钮。
- 学校管理员不能调用平台管理员积分接口，即使目标成员属于本校也不允许。
- 老师、学生和普通用户不能读取平台端跨校成员列表，不能调整本人或他人的积分。

## 6. 页面与交互

入口位于管理后台“学校管理”。学校列表每行和移动端卡片增加“成员”操作，点击后打开响应式成员抽屉。

### 6.1 成员抽屉

成员抽屉包含：

- 当前学校名称和状态。
- 搜索框：按公开账号 ID、用户名、姓名或邮箱进行服务端搜索。
- 筛选项：老师/学生、可用/停用。
- 分页成员列表。
- 成员账号、公开账号 ID、校内身份、成员状态、账号状态。
- 永久积分、每日积分和总积分。
- 平台管理员可见的“调整积分”操作。

成员数据必须按学校 ID、关键词、身份、状态和分页定向查询。浏览器不能读取全站用户或整张成员表后自行筛选。

抽屉不使用 Ant Design 固定 `size="large"`。桌面使用不超过可视区的响应式宽度，390px 和 430px 使用不超过 `100vw` 的布局，成员列表和底部操作不得横向溢出。

### 6.2 调整积分弹窗

弹窗使用分段控件选择“增加”或“扣减”，并展示：

- 学校名称。
- 成员姓名与公开账号 ID。
- 账号和成员状态。
- 当前永久积分。
- 调整数量。
- 调整后预计永久积分。
- 必填的调账原因。

调整数量必须大于零，支持两位小数。扣减后的预计永久积分低于零时，前端阻止提交；服务端仍需独立校验，不能信任前端结果。

提交期间禁用确认按钮。成功后关闭弹窗、刷新当前成员行并展示新的永久积分和总积分；失败时保留用户输入并显示服务端返回的中文原因。

学校、成员或账号处于停用状态时仍允许平台管理员调整积分。界面必须明确提示“停用账号当前不能生成”，避免把余额调整误解为恢复账号。积分调整不会改变学校、成员或账号状态。

## 7. API 与类型

新增平台管理员接口：

```text
GET  /api/admin/schools/{schoolId}/members
POST /api/admin/schools/{schoolId}/members/{membershipId}/points-adjustments
```

接口继续使用 `{ code, data, msg }` 响应结构。

成员查询支持：

```ts
type AdminSchoolMemberQuery = {
    page?: number;
    pageSize?: number;
    keyword?: string;
    role?: "teacher" | "student";
    status?: "active" | "disabled";
};
```

平台成员积分视图使用独立返回类型，不向普通学校成员响应追加钱包字段：

```ts
type AdminSchoolMemberPoints = SchoolMember & {
    userId: string;
    accountStatus: "active" | "disabled";
    permanentPoints: number;
    dailyPoints: number;
    totalPoints: number;
    dailyPointsExpiresAt: string;
};
```

调账请求：

```ts
type AdminSchoolMemberPointsAdjustmentInput = {
    operation: "credit" | "debit";
    amount: number;
    reason: string;
    idempotencyKey: string;
};
```

调账成功返回：

```ts
type AdminSchoolMemberPointsAdjustmentResult = {
    member: AdminSchoolMemberPoints;
    adjustment: {
        recordId: string;
        operation: "credit" | "debit";
        amount: number;
        balanceBefore: number;
        balanceAfter: number;
        reason: string;
        createdAt: string;
    };
};
```

Route Handler 只解析请求、校验管理员 Session、调用服务并映射响应。学校归属校验、金额校验、钱包事务和结果组装放在 `web/src/lib/server/`；数据库读取沿用 repository；前端请求放在 `web/src/services/api/admin-education.ts`。

## 8. 服务端流程

### 8.1 查询成员

1. 校验当前用户是状态正常的全局 `admin`。
2. 按 `schoolId` 查询学校，不存在时返回 404。
3. 按学校、关键词、身份、状态和分页查询成员，数据库查询同时关联用户账号。
4. 读取当前页成员的永久积分与当日钱包，不读取全站钱包或整表快照。
5. 返回平台管理员专用的成员积分视图。

### 8.2 调整积分

1. 校验当前用户是状态正常的全局 `admin`。
2. 校验 `operation`、正数金额、非空原因和幂等编号。
3. 在事务或文件 Provider 的串行写入边界内，按 `schoolId + membershipId` 锁定并读取成员关系。
4. 验证成员用户存在，且该成员关系确实属于请求学校。
5. 将 `credit` 映射为正差额，将 `debit` 映射为负差额。
6. 调用现有永久积分钱包调整能力，停用账号使用管理员调账专用的 `requireActive: false` 语义，最低余额固定为零。
7. 写入 `admin-adjust` 积分流水，流水金额使用带符号的实际变化值，余额快照使用操作完成后的真实钱包余额。
8. 记录管理员审计日志，返回更新后的成员积分视图和调账结果。

同一个幂等编号只能对应同一个管理员、学校、成员、操作、数量和原因。完全相同的重复请求返回原结果；参数不同但复用同一编号时返回 409，不能静默复用或重复入账。

## 9. 流水与审计

个人积分流水沿用现有 `point_records`：

- `type`：`admin-adjust`。
- `amount`：增加为正数，扣减为负数。
- `permanent_amount`：与 `amount` 相同。
- `daily_amount`：始终为零。
- `description`：保存平台管理员填写的调账原因。
- `idempotency_key`：保存本次稳定提交编号。
- `balance_after`、`permanent_balance_after`、`daily_balance_after`：保存事务完成后的余额。

管理员审计日志使用独立动作 `admin.school-member.points-adjust`，包含：

- 操作管理员。
- 学校 ID 和学校名称。
- 成员关系 ID、用户 ID、公开账号 ID和显示姓名。
- `credit` 或 `debit`。
- 调整数量、永久积分操作前后余额。
- 人工填写的原因。
- 积分流水 ID和幂等编号。
- 成功或失败状态。

积分流水和审计日志不能通过本功能删除。错误调账使用新的反向调整修正，并填写新的原因。

## 10. 异常处理

- 未登录返回 401。
- 非全局 `admin` 返回 403。
- 学校、成员不存在或成员不属于该学校返回 404，避免泄露跨校实体存在性。
- 操作类型无效、数量不是正数、原因为空或幂等编号为空返回 400。
- 扣减超过当前永久积分返回 409，并返回“个人永久积分不足”。
- 同一幂等编号对应不同参数返回 409。
- 调账过程中任一步失败时，余额和积分流水一起回滚；审计日志记录失败结果，不返回半成功状态。
- 页面查询失败保留当前学校和筛选条件，提供显式刷新；调账失败保留弹窗输入。

## 11. 测试与验收

### 11.1 服务与持久层

- 全局管理员可以查询学校 A 和学校 B 的成员，不需要 `education.manage` 或 `billing.manage`。
- 普通用户、学校管理员、老师和学生不能调用平台接口。
- 学校 A 的请求不能使用学校 B 的成员关系 ID 调账。
- 搜索支持公开账号 ID、用户名、姓名和邮箱，身份、状态和分页条件在数据库中生效。
- 增加和扣减永久积分正确写入带符号流水，操作前后余额正确。
- 使用至少一个非整数金额验证 PostgreSQL `numeric` 语义。
- 扣减不能低于零，每日积分保持不变。
- 相同请求重复提交只入账一次，不同参数复用幂等编号返回冲突。
- 停用学校、停用成员和停用账号仍可调账，但不会被自动启用。
- PostgreSQL 调账使用真实事务；涉及共享测试库的 Schema、清理或锁测试使用 `--no-file-parallelism`。
- 文件 Provider 在余额、流水或成员读取失败时保持原状态。

### 11.2 Route 与前端

- Route 校验 Session、参数和 `{ code, data, msg }` 映射。
- 所有平台管理员都能看到学校列表和成员入口；没有原职责权限时仍不能新建或编辑学校。
- 成员抽屉按公开账号 ID、用户名、姓名或邮箱搜索并显示真实余额。
- 调账弹窗必须选择操作、填写正数金额和原因，并展示预计余额。
- 余额不足、跨校 ID、重复提交冲突和服务端失败显示明确中文错误。
- 成功后只刷新当前成员数据，不重新加载全站用户。
- 学校后台和普通用户端不出现积分调整入口。

### 11.3 浏览器与全量质量门禁

- 在桌面、390px、430px 验证学校列表、成员抽屉、搜索、分页和调账弹窗。
- 检查浅色/深色、按钮 hover/disabled、抽屉宽度、底部操作区和无横向溢出。
- 使用正常语义点击完成增加和扣减，不使用 `force`、固定延时或重试掩盖交互问题。
- 运行相关单元测试、Route 测试、PostgreSQL 集成测试、类型检查及项目 Mandatory Testing。
- 严格 UTF-8 解码本次修改的文本文件，并检查 `U+FFFD` 和常见乱码组合。

## 12. 最终验收

平台管理员进入“学校管理”，选择任意学校后可以搜索该校成员，并对指定成员的个人永久积分执行有原因、可追溯、幂等的增加或扣减。扣减不会产生负余额，每日积分不变，停用状态不被修改。学校管理员、老师、学生和普通用户无法使用该能力；个人积分、学校算力池、制作小组额度和商单扣费顺序保持既有边界。
