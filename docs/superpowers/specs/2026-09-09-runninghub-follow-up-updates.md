# RunningHub 后续更新记录：API Key 工作流目录拉取

## 1. 需求记录

第一版先按同事 Demo 完成已知 `workflowId` 的单条工作流读取、保存、测试和启用。后续希望支持管理员使用当前 RunningHub API Key，读取该 Key 有权限访问的本人工作流目录，选择工作流导入平台。

## 2. 不属于第一版

第一版只支持：

```text
平台已保存 workflowKey
→ 读取其中的 RunningHub workflowId
→ API Key + workflowId 拉取最新 API JSON
→ 保存并继续测试/启用
```

第一版不实现：

- 自动读取账号下全部工作流；
- 工作流目录分页；
- 工作流名称搜索；
- 批量导入；
- 未确认工作流自动进入无限练习；
- 通过列表结果直接自动启用。

## 3. 后续目标流程

```text
管理员点击“读取我的 RunningHub 工作流”
    ↓
服务端使用当前渠道 API Key 调用 RunningHub 官方工作流列表接口
    ↓
展示该 Key 有权限访问的工作流 ID、名称、更新时间和状态
    ↓
管理员选择一条工作流
    ↓
按 workflowId 拉取 API JSON
    ↓
分析输入节点、节点映射和输出节点
    ↓
管理员确认 workflowCode 和映射
    ↓
保存为平台工作流草稿
    ↓
真实测试
    ↓
测试成功后启用
```

拉取目录只是“发现和导入候选”，不替代第一版的工作流配置、测试和启用门槛。

## 4. 开发前必须确认的上游契约

在 RunningHub 官方文档或真实 fixture 证据确认前，不得猜测接口路径或字段。实施前必须确认：

- 工作流列表接口的真实 HTTP 方法和路径；
- API Key 的真实鉴权方式；
- API Key 可见范围；
- 分页、搜索、排序参数；
- 工作流 ID、名称、更新时间、状态字段；
- 是否支持只返回当前用户创建的工作流；
- 列表中的 Workflow ID 是否可以继续调用 Demo 已验证的 JSON 拉取接口；
- 上游是否限制列表结果数量或请求频率。

如果官方没有提供可验证的工作流列表接口，则保留第一版的 Workflow ID 手工录入/初始化 Demo 方式，不自行伪造目录接口。

## 5. 后续设计边界

后续实现仍必须遵守：

1. RunningHub 只服务无限练习；
2. 工作流是唯一业务配置对象；
3. 不重新引入上游模型、伪模型、逻辑模型绑定或练习默认模型；
4. 导入候选必须绑定明确的 `workflowCode`；
5. 导入后继续使用第一版的“拉取 JSON → 保存 → 测试 → 启用”闭环；
6. 不修改无限练习前端页面，除非后续明确提出新的交互需求。
