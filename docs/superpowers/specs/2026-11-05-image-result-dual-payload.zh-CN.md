# 图片结果同时带 base64 和地址时不再二次下载

日期：2026-11-05
状态：待批准后实现
范围：`web/src/app/api/image-tasks/image-task-support.ts` 的结果解析，加回归测试。不改表结构，不动生产配置。

## 背景

生产任务 `c5698a68-fecc-4fc3-a542-852cc3f9ec9f`（2026-11-05 11:11，模型 `gpt-image-2.5`，渠道空集 `QGWp1ZvPRmRjlsuBaJhN2`，画布节点 `xYrMN_j8cOdQ0-KibTyoX`）图已经生成成功，但任务被判失败，前端显示"网络异常，请点击重试"。

诊断事件：

1. 11:12:06 上游 `/v1/images/edits` 返回 200，响应体 4,100,013 字节，同时带 `b64_json` 和 `url`。
2. 11:12:07 第一张图读完，186 毫秒，1024×1536，3,074,679 字节，来自响应里的 base64。
3. 同一秒又去下载响应里的 `url`（`http://152.69.215.43:13000/images/...`）。60 秒内只下了 2,600,608 / 3,074,679 字节，触发 `media_timeout`。
4. `image-task-result-service.ts` 对画布任务规定：结果列表里任意一项读取失败就整单失败。已经到手的图被一起报废。

本地实测同一地址 2 秒能下完，生产服务器在国内下这个地址要一分多钟，所以只有生产会踩到。

## 原因

`collectImageResults` 对同一个对象既收 `b64_json` 又收 `url`，两个都推进结果列表。`dedupeImageResults` 只按内容去重，认不出"同一张图的两种形式"。下游对列表每一项都做媒体读取，第二个地址一超时就把整单判失败。

base64 解码出来就是原图，和那个地址上的文件是同一份（字节数一致）。前端最终拿到的是存进我们自己存储后的地址，不依赖上游给的 `url`。

## 改法

在 `collectImageResults` 里，一个对象已经从 `IMAGE_BASE64_KEYS` 拿到图片时，不再收集它自己的 `IMAGE_URL_KEYS`。嵌套对象照旧递归，多张图的响应不受影响。

只跳过"同一个对象上附带的地址"。只有地址、没有 base64 的结果保持原样，继续走下载。

## 测试

`web/src/app/api/image-tasks/image-task-support.test.ts` 加一条：输入 `{ data: [{ b64_json: <一张小 PNG 的 base64>, url: "http://example.invalid/slow.png" }] }`，断言 `findImageResults` 只返回 1 项，且是 data URL，不含那个地址。

已有的"只有 url""url 和 b64 来自不同对象"的用例保持通过，确认没有误伤。

## 不改的

- `image-task-result-service.ts` 的"画布任务任一失败即整单失败"不动。那是为了避免画布拿到残缺结果，这次的问题在结果不该被拆成两项。
- 不改渠道配置，不改 `response_format`。空集这个模型不管请求什么格式都同时返回两种，靠请求参数去不掉。
- 生产配置（空集绑定的开关）由管理员在后台操作，本改动不碰数据库。

## 发布

改动在服务端解析，随下一次发布生效。发布前生产上该模型的空集绑定保持关闭，否则每次都会复现。
